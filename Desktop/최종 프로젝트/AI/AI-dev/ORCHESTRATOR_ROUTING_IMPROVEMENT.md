# Orchestrator 라우팅 로직 개선

## 문제점

1. **원래 문제**: 문서 작성 요청에 "일정" 키워드가 포함되어 schedule 도메인으로 잘못 라우팅
2. **지적된 문제**: 단순 "문서" 키워드만으로도 document로 라우팅되어, 일정 페이지에서 "문서 관련 일정" 같은 요청도 document로 잘못 라우팅될 수 있음

## 개선된 라우팅 로직

### 우선순위 기반 분류

**우선순위 1: 문서 작성 액션 키워드 (최우선)**
- "문서 작성해줘", "문서 생성", "보고서 작성해줘", "양식:", "제품개발 계획서" 등
- **예시**:
  - ✅ "문서 작성해줘. 양식: ... 일정: ..." → `document` (문서 작성이 주 목적)
  - ✅ "문서 작성해줘. 요구사항: Q1, Q2 일정 포함" → `document`

**우선순위 2: 문서 검토/조회 + 일정 키워드**
- "문서 검토", "문서 확인", "문서 조회" + "일정" 키워드
- **예시**:
  - ✅ "문서 검토 일정 알려줘" → `schedule`
  - ✅ "문서 확인 일정은 언제야?" → `schedule`
  - ✅ "문서 관련 일정 보여줘" → `schedule`

**우선순위 3: Schedule 키워드**
- "일정", "연차", "반차", "병가", "회의실", "예약" 등
- **예시**:
  - ✅ "내일 연차 신청하고 싶어" → `schedule`
  - ✅ "오후 회의실 예약해줘" → `schedule`

**우선순위 4: 다른 도메인 키워드**
- "특허", "논문" → `tech`
- "메일", "이메일" → `email`
- 등등...

**우선순위 5: 단순 문서/보고서 키워드**
- 문서 작성 액션이 없고, schedule 키워드도 없는 경우
- **예시**:
  - "문서 목록 보여줘" → `document`
  - "보고서 양식은 뭐야?" → `document`

## 개선 효과

### ✅ 해결된 문제들

1. **문서 작성 요청이 schedule로 잘못 라우팅되는 문제**
   - 문서 작성 액션 키워드가 최우선으로 체크됨
   - 요구사항에 "일정" 키워드가 있어도 document로 올바르게 라우팅

2. **일정 관련 문서 요청이 document로 잘못 라우팅되는 문제**
   - 문서 검토/조회 키워드 + 일정 키워드 조합을 체크
   - "문서 검토 일정" 같은 경우 schedule로 올바르게 라우팅

### 테스트 시나리오

#### ✅ 정상 동작 예시

1. **문서 작성 요청**:
   ```
   입력: "문서 작성해줘. 양식: 제품개발 계획서, 제목: 2024년 스마트워치 신제품 개발 계획서. 요구사항: Q1 일정, Q2 일정 포함"
   결과: document 도메인으로 라우팅 ✅
   ```

2. **문서 검토 일정 요청**:
   ```
   입력: "문서 검토 일정 알려줘"
   결과: schedule 도메인으로 라우팅 ✅
   ```

3. **일반 일정 요청**:
   ```
   입력: "내일 연차 신청하고 싶어"
   결과: schedule 도메인으로 라우팅 ✅
   ```

4. **일반 문서 조회**:
   ```
   입력: "문서 목록 보여줘"
   결과: document 도메인으로 라우팅 ✅
   ```

#### ⚠️ 경계 케이스

1. **"문서 작성해줘. 문서 검토 일정도 포함해줘"**
   - 현재 로직: `document`로 라우팅 (문서 작성 액션이 최우선)
   - 판단: ✅ 적절함 (문서 작성이 주 목적이므로)

2. **"문서 검토 일정과 문서 작성 요청 모두 해줘"**
   - 현재 로직: `document`로 라우팅 (문서 작성 액션이 최우선)
   - 판단: ✅ 적절함 (문서 작성이 주 목적이므로)

3. **"문서 관련 일정"** (문서 작성 액션 없음)
   - 현재 로직: `schedule`로 라우팅 (문서 검토 + 일정 키워드)
   - 판단: ✅ 적절함

## 추가 개선 제안

### 향후 개선 방향

1. **LLM 기반 분류 강화**
   - 키워드 매칭만으로 판단하기 어려운 경우 LLM으로 분류
   - 현재는 Structured Output Parser로 fallback 처리

2. **대화 컨텍스트 활용**
   - 이전 대화 히스토리를 고려한 분류
   - 현재도 부분적으로 구현되어 있음

3. **의도 점수화**
   - 각 도메인에 대한 신뢰도 점수 계산
   - 가장 높은 점수의 도메인으로 라우팅
